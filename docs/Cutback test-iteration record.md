## 1. 前期测试

第一版评测使用 18 条开发集用例，状态判断准确率为 **88.9%（16/18）**，编辑动作准确率为 **100%（6/6）**。最主要的问题是模型会把“这里有点拖”这类负面评价直接理解成删除操作，存在明显的**越权执行**风险。

→明确原则：

> **Location ≠ Intent ≠ Permission**

也就是说，时间码只能说明用户在说哪里，负面评价只能说明用户对这部分不满意，都不等于用户已经授权 AI 修改。

调整决策规则后，开发集准确率提升到 **94.4%（17/18）**，12 条未参与 Prompt 调整的留出集全部通过；之后新增 `MOVE_RANGE`，相关测试全部通过，重新运行原有测试后也没有观察到明显能力回退。

## 2. 产品发布后的自测迭代

发布后继续实际使用，又发现了测试集没有暴露出来的问题：

1. **AI 过于保守**：大量本可以继续处理的输入统一返回 `CLARIFY`。
  → 调整 Prompt，减少不必要的澄清，避免“安全”本身变成额外交互成本。
2. **随后又出现** `NO_ACTION` **使用过度的问题**：只要一句话涉及当前不支持的动作，系统就倾向于直接拒绝。
  → 重新明确三个状态的边界：
  - 信息足够且当前功能支持 → `ACTION`
  - 用户补充必要信息或调整表达后即可执行 → `CLARIFY`
  - 意图已经明确，但操作本身超出当前能力 → `NO_ACTION`
3. `CLARIFY / NO_ACTION` **的提示不够清楚**：系统会告诉用户下一步怎么做，却没有解释为什么当前不能执行。
  → 要求两种状态都必须通过 `message` 说明具体原因，并给出下一步可以采取的动作。

整个调整继续遵循同一个原则：每一种状态都必须有明确存在的理由。权限控制的目标是减少错误执行，而不是为了“更安全”增加没有必要的确认和拒绝。

## 3. 剪辑师测试反馈

邀请一位有剪辑经验的业余剪辑师实际测试后，我发现当前版本最明显的瓶颈已经不是三状态策略，而是**基础能力覆盖不足**。

真实 Review 至少还需要进一步覆盖：

- 视频语义理解和内容定位；
- 将一条自然语言拆分成多个编辑操作；
- 再根据实际使用频率逐步加入字幕、音轨及更多基础剪辑动作。

因此现阶段并不适合直接扩大用户测试。当前能力范围过窄时，大量 `CLARIFY / NO_ACTION` 实际上只是功能缺失的结果，很难据此判断 Review-to-Edit 是否真的提高了效率。

## 4. 当前结论

当前版本已经验证了 Agent 的基础权限机制、三状态决策和结构化编辑流程，但还不能证明它真正提高了真实 Review → Edit 的效率。

下一步优先补齐：

> **最小视频语义理解 + Multi-action Parsing**

完成这两项基础能力后，再通过真实用户的 **Accept / Modify / Reject、未经授权执行次数、Clarify 次数和修改耗时**，判断三状态机制究竟是在降低 Review-to-Edit 的成本，还是只是增加了一层新的交互成本。
