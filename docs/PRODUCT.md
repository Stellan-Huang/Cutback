## 产品命题

Cutback 不是一个“自动剪辑器”，也不试图替代 Premiere、Resolve 或 CapCut。它处理的是视频生产里一个更具体的问题：一版视频完成后，审核者留下自然语言修改意见，剪辑者需要重新理解、定位时间线、判断修改方式，再把意见转成可执行的编辑操作。真正消耗时间的往往不是某一次点击，而是 Review 到 Edit 之间反复发生的理解、确认和返工。Cutback 希望把这一层变成产品能力：将自然语言 Review 转成结构化、可确认、可执行的时间线操作，同时避免 AI 在没有充分授权时擅自修改作品。

这个项目来自我对 AI Creator / AI Video Workflow 的前期研究。相比“生成一段视频”，专业创作更接近一条连续工作流：素材理解、粗剪、审核、修改、版本确认和交付。模型越来越擅长理解和生成内容，但模型能力不会自动变成产品价值。专业创作真正关心的是 AI 能否理解项目上下文、保留用户控制权，只修改用户真正允许修改的部分。Review-to-Edit 因此成为一个合适的切入口：AI 不需要自己判断“什么是好作品”，而是先处理人已经表达出来的修改意图，把“审核者 → 制片 / 项目负责人 → 剪辑者”之间的信息传递，缩短为“审核者 → Agent → 用户确认 → 时间线”。

Cutback 的第一性目标有两个：提高 Review 到 Edit 的转换效率；降低 AI 越权执行带来的返工和不信任。后者是前者的约束。如果 AI 为了追求自动化率，把模糊评价直接解释成删除或移动，用户可能花更多时间检查和恢复，产品反而制造新的工作。因此 Cutback 不只关注“Agent 能做多少”，也关注“它是否知道什么时候不能做”。

## 产品设计

V0 只验证一个问题：**Review 能否被可靠理解，并转化为用户愿意执行的视频编辑操作。** 它不验证完整自动剪辑，也不构建完整的非线性剪辑软件（NLE）。核心流程是 `Review → 理解 → 确认 → 规划 → 执行 → 预览`。每条 Review 首先被判断为 `ACTION`、`CLARIFY` 或 `NO_ACTION`：`ACTION` 表示意图和参数明确，且系统具备执行能力；`CLARIFY` 表示存在修改意图，但缺少必要信息或授权；`NO_ACTION` 表示认可、保留、无需修改，或当前系统无法执行。只有用户确认的 `ACTION` 才进入时间线规划，并由确定性执行层完成修改。

Cutback 最重要的产品规则是：**Location ≠ Intent ≠ Permission**。位置不等于意图，意图也不等于授权。时间码只说明用户在谈哪里，不代表他想怎么改，更不代表已经授权系统执行。例如“00:10–00:20 这里有点拖”表达了不满意，但没有说明应该删除、加速还是重剪，因此返回 `CLARIFY`；“00:10–00:20 这段删掉”同时包含位置、动作和授权，才生成 `DELETE_RANGE`。这条规则来自早期 Bad Case：第一版评测中，模型曾把负面评价错误解释为删除授权。对于创作工作流，多一次确认的成本通常低于一次错误修改。

V0 当前只支持两种时间线操作：`DELETE_RANGE` 和 `MOVE_RANGE`。LLM 负责理解 Review 并生成结构化决策，Pydantic 负责约束输出结构和参数合法性，时间线规划器负责把多条已批准操作统一转换成最终时间线，FFmpeg 负责确定性执行。AI 不直接修改视频：语义理解可以存在不确定性，但执行层不能。多条 Review 也不会按照输入顺序直接修改文件，而是统一基于原始时间线坐标进行规划；如果出现源区间重叠、移动目标冲突等情况，V0 不猜测执行顺序，而是停止自动执行，让用户调整相关操作。

```text
Review
↓
ACTION / CLARIFY / NO_ACTION
↓
结构化 EditAction
↓
用户确认
↓
时间线规划
↓
冲突检查
↓
FFmpeg 执行
↓
原视频 / 修改后视频预览
```

这个范围是有意收窄的。V0 没有做完整 NLE、Premiere / Resolve 插件、Frame.io 集成、多轨编辑、字幕、音频、B-roll、生成式视频、风格记忆、模型路由，也不支持“刚才那句话”“第二次出现产品时”这类复杂语义定位。在核心假设尚未跑通之前扩展整个视频编辑动作空间，只会增加复杂度并模糊验证结果。Cutback 先跑通自然语言决策、授权边界、结构化编辑动作、人工确认和确定性执行这条链路，再决定下一步扩展语义定位还是动作覆盖范围。

## 评测与迭代

评测从一开始就是产品设计的一部分。第一版内部评测覆盖 Review 状态判断准确率、EditAction 准确率、留出集验证、回归测试、响应延迟和 Bad Case 分析。初始开发集的 Review 状态判断准确率为 16/18（88.9%），主要 Bad Case 是把“负面评价”误解成“删除授权”。基于这个问题，我收紧了决策规则，明确区分 Location、Intent 和 Permission。迭代后开发集达到 17/18（94.4%），未参与 Prompt 调整的 12 条留出集全部通过；`DELETE_RANGE` 动作测试通过，新增 `MOVE_RANGE` 后相关测试也全部通过，回归测试没有观察到明显能力回退。

这些数字只说明 V0 在既定测试范围内的决策边界更稳定，不代表产品已经被真实创作者充分验证，也不代表 Review-to-Revision 的效率已经提升。当前更重要的判断是：随着决策规则稳定下来，瓶颈正在从“模型会不会乱做决定”转向“真实 Review 能否被当前能力覆盖”。真实修改意见还会涉及语义定位、倍速、音轨、字幕、对齐、B-roll、节奏和多轨操作，用户也更自然地说“刚才那句话”而不是始终提供精确时间码。因此对 V0 来说，动作覆盖范围和语义定位能力，比继续提高分类准确率更值得投入。

因此我选择在这个阶段停止继续堆功能。当前版本已经完成从 Review 到真实视频修改的可运行闭环，也暴露了下一阶段需要验证的问题。继续开发时，更合理的路径是先收集自然 Review，建立“位置 / 意图 / 动作 / 授权”的分类体系，根据高频需求选择新增动作，再引入转写文本、镜头信息和多模态上下文做语义定位。之后再通过真实用户测试记录 Accept / Modify / Reject、未经授权执行率、澄清次数、Review-to-Revision 时间和主要 Bad Case。只有这些数据出现后，才能判断 Cutback 是否真正降低了从 Review 到 Revision 的操作成本。

## 当前结论

Cutback v0.1 是一个产品假设的可运行证明，而不是可以直接进入专业生产环境的剪辑工具。它已经证明：自然语言 Review 可以被拆成明确的决策状态；明确授权的修改可以转换成结构化时间线操作，并由确定性执行层落到真实视频；Agent 的关键问题不仅是“理解得准不准”，还包括“什么时候没有权限执行”。它尚未证明真实创作者是否愿意长期使用这套交互，以及在更完整的动作覆盖范围下，Review-to-Edit 是否真的比现有流程更快。

因此我没有继续把 Demo 扩成一个小型 NLE，而是把已经成立的闭环、暴露的 Bad Case 和尚未验证的问题明确分开。Cutback 最有价值的结果不是增加了多少 AI 功能，而是把“AI 帮我改视频”压缩成了一个可以实现、评测和继续迭代的产品问题：**AI 能否在不夺走用户控制权的前提下，把 Review 更高效地变成 Edit。**
